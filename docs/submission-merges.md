# 重复提交与申请合并

开发者输入游戏名称或 Steam 链接后，表单检查其本人已有的申请。比较三语名称（Unicode NFKC、忽略大小写、空格和标点），也比较 Steam App ID。提示仅面向当前账号，包含已上架、待审核、驳回和已合并的历史记录。同名可能属于不同游戏，开发者可勾选“我确认仍要新增一条申请”继续提交；新记录仍需独立审核。

服务端创建接口再次检查重复。未确认时返回 `409 duplicate_confirmation_required` 和当前账号的匹配记录，确认时接受 `allow_duplicate: true`。浏览器为一次提交生成 `submission_key`，网络重试复用该键；成功后或表单内容改变时生成新键。同一键和相同内容只创建一条记录，键复用但内容不同返回 409。数据库唯一索引处理同时到达的重试。

管理员在“游戏审核”展开需要归档的重复申请，点击“合并到其他申请…”，选择同一开发者的保留记录，确认合并。名称或 Steam App ID 匹配的记录优先显示，并优先选择已上架记录。管理员可核对后选择其他同账号记录；跨账号合并不允许。已通过的来源必须合并到已通过的目标，正在展示的来源还要求目标正在展示。

保留记录的正文、图片、审核状态、归属等资料保持原值。来源申请保留全部原内容，记录 `merged_into`、合并时间、管理员及备注，将状态改成 `merged`、可见性改成 0，并保留此前的状态和可见性。条件更新检查两条记录的状态及归属，避免并发合并产生循环或覆盖过期状态。重复请求同一合并返回已完成。

后台“已合并”栏目可查看原申请的三语正文和素材；待审核及精选申请计数排除已合并记录。已合并内容作为历史资料查阅，不能重新通过、编辑、翻译或申请精选；管理员仍可明确确认后删除历史申请。开发者账号中心保留来源和保留记录两张卡片，来源显示三语“已合并”，并注明当前保留记录；已合并申请不再提供开发者删除入口。连续合并时，链接解析至最后的有效保留记录。

合并关联申请记录；如需采纳来源中的新资料，可查阅历史后编辑保留记录。管理员选择并确认需要合并的记录，不根据名称自动归档现有申请。

## 数据库

发布前应用 `migrations/20261026_game_submission_merges.sql`。新增 8 个可空字段及两个索引，原申请内容和状态保持原值。`merged_into` 和 `merged_by` 使用外键；目标游戏或管理员被明确删除时相应引用置空，来源历史记录保留。测试 schema 包含这些字段，其他本地数据库也需应用本迁移。

```sh
NODE_PATH=/workspace/.setup-tools/node_modules node --test tests/submission-merges.mjs
# 本地静态服务监听 8811 后：
NODE_PATH=/workspace/.setup-tools/node_modules node tests/submission-merges-browser.cjs
```

本地 D1 检查确认后重复提交、请求重放、并发提交、跨账号保护、保留已上架记录、原内容保留、合并状态过滤、私有历史、连续合并和相反方向的并发合并。浏览器检查三语提示、继续提交、重试复用、确认合并、后台历史与开发者双卡片展示。测试不合并生产申请。
